# Trading Platform Review — Final Report
Snapshot: commit fc86359 (review-snapshot). 44 raw findings survived adversarial verification; duplicates across review dimensions have been merged below into 24 distinct defects. All paths are relative to `backend/src/trading/` unless noted.

## 1. Verdict

The architecture is doing what it promises in the places that are hardest to get right: there is no path to `PlaceOrder` that bypasses `RiskGate.evaluate`, the provenance wall (execution_barred / `tradeable_signals`) correctly fails closed, the event log's append-only invariant is genuinely DB-enforced, and money arithmetic is Decimal-clean. **Paper trading in the current manual/collect-only cron mode is acceptable to keep running today** — with the caveat that the event log is already accumulating duplicate signal events every day (Finding 1), so the recorded conviction/proposal history you are using to judge the algo is inflated and the corruption is permanent.

**Do not enable CYCLE_TRADE_MODE=auto** until Finding 1 is fixed: the daily cron replays the entire 21-day lookback on every run, and the trading path (unlike every UI surface) counts every duplicate, so conviction scores inflate linearly day over day and will cross the trade threshold on fabricated corroboration.

**Do not enable ALLOW_LIVE** until, at minimum, all of these are closed:
1. Ingestion idempotency (F1) — persisted cursors or signal-id dedupe on the trade path.
2. Kill switch rehydration (F2) — today the emergency stop cannot reach the process that trades and silently disengages on every redeploy.
3. Drawdown breaker (F3) — the max-drawdown circuit breaker is structurally incapable of tripping in the cron deployment.
4. Price provenance (F4) — real-broker orders can be risk-sized against $200 synthetic sector constants, defeating the notional caps ~4x, precisely in the pre-open window the cron runs in.
5. Order idempotency + serialization (F5, F6) — any retry or overlapping evaluation doubles a position; the idempotency key is minted fresh per attempt so it can never fire.
6. Fill ingestion (F7, F8, F9, F14) — under documented defaults no fill is ever recorded; when enabled, the two fill paths have incompatible idempotency models, a partial-fill freeze, a duplicate-record race, and a SELL-before-BUY wedge that permanently halts sync.
7. Mode-routed reconciliation (F15) — the live account would never be reconciled at all.
8. Fail-closed auth (F12) and a guard against MODE_DEFAULT=live (F10).

## 2. Findings (ranked)

### CRITICAL

**F1. Daily cron replays the whole lookback window; the trading path double-counts every duplicate, inflating conviction linearly until it trades on fabricated corroboration**
`application/ingest_signals.py:49`, `application/political_cycle.py:56`, `domain/conviction.py:258-263`, `jobs/cycle.py:58` (merged: 3 findings)
- Scenario: cursors are an in-memory dict seeded to `now - 21d` in every fresh process; the cron is a fresh process daily. Deterministic signal ids (`house-{doc_id}-…`, `sec-form4-…`) are re-fetched and re-appended every run — up to ~21 copies per signal, permanently, in an append-only log. `PoliticalCycle` builds its window from the RAW log via `signals_from_events` (no signal-id dedupe), and `compute_conviction` does `decayed_weighted_sum += contribution` per copy (identical timestamps, so decay doesn't attenuate). A single House PTR worth ~6 points reaches ~90+ after ~15 runs and crosses the trade threshold (70); inflated scores also suppress legitimate exits. `rm_signals` dedupes on its PK, so /signals and /proposals look correct — the inflation is invisible everywhere except the path that places orders. The cycle.py docstring's claim that runs inherit prior cursors is false.
- Fix sketch: persist ingest cursors (small table or a cursor event replayed at build time) AND dedupe by signal id at the point of use — `signals_from_events` should keep first-occurrence-per-signal_id (this also heals the already-corrupted log for replay consumers). Optionally add append-time idempotency: refuse a second `signal.received` on an existing `signal-{id}` stream. Also fix the audit invariant: `contributions` collapses duplicates by id while the sum counts them, so contributions no longer sum to the score.

### HIGH

**F2. Kill switch is process-local and never rehydrated — it does not reach the cron that trades, and any redeploy silently disengages it** (critical the day ALLOW_LIVE flips)
`main.py:171`, `application/risk.py:27-28`, `interface/app.py:492-514`
- Scenario: POST /kill-switch flips only the web process's in-memory bool and appends a `KILL_SWITCH_CHANGED` event that nothing ever reads back. The next 13:00 UTC cron builds a fresh `KillSwitch()` (`_engaged=False`) and trades straight through. Any Render redeploy of the web service resets an engaged switch with no operator action.
- Fix sketch: in `build_dependencies`, replay the last `KILL_SWITCH_CHANGED` event and seed the switch from it; the cron gets this for free. Add a test pinning cross-process/startup rehydration.

**F3. Max-drawdown circuit breaker is structurally dead: peak equity is in-memory per process, so the one-shot cron always computes drawdown = 0**
`application/evaluate_signals.py:65,96`, `application/risk.py:77-79`, `main.py:352` (merged: 2 findings)
- Scenario: `_peak_equity` starts at 0 and is set to `max(0, current equity)` immediately before the risk check — in a fresh process peak == current, drawdown == 0, always. The account can grind down 50% over weeks of daily runs and the mandatory `max_drawdown_pct` cap never rejects an order. Restarts of the always-on API have the same reset. `PORTFOLIO_SNAPSHOT` events with equity exist in the log and are never used.
- Fix sketch: seed the peak at startup from max equity across `PORTFOLIO_SNAPSHOT` events (or a persisted watermark). The existing unit test injects the peak directly and so hides this — add a test through `EvaluateSignals`.

**F4. Real-broker orders are risk-sized against synthetic static sector prices whenever the live quote falls back — precisely the pre-open window the cron runs in**
`infrastructure/market_data/feed_backed.py:26-28`, `main.py:246`, vs the invariant at `main.py:314-326` (merged: 2 findings)
- Scenario: at 13:00 UTC (09:00 ET) IEX pre-market is often empty; `AlpacaMarketData` returns no quote or last=0, and `FeedBackedMarketData` silently falls back to `_DEV_PRICES` (every TECHNOLOGY ticker = $200). A ~$900 stock is checked against max-trade/concentration caps at $200 notional, passes, and fills at the open at ~4.5x the intended exposure. The decision event's recorded `market_context` is the fake price, so the audit trail is wrong too. The startup guard ("a real account must never trade or mark against synthetic prices") only checks the feed is configured, not each quote.
- Fix sketch: when `require_real_data`, do not wire the static fallback at all; a missing/non-positive live quote should skip that symbol's decision with a logged reject, never substitute a price. Tag Quote with a provenance field if you want the fallback for dev display.

**F5. Duplicate order submission on re-run/retry: pending open orders are invisible to sizing and the idempotency key is never reused**
`application/evaluate_signals.py:197` (key minted at :119), `sync/paper dedupe at brokers/paper.py:50-52`, `brokers/alpaca.py:86-88`
- Scenario: cron places a DAY order pre-open; it queues unfilled until 09:30 ET. Any second evaluation in that window (crash-retry after a mid-loop `UnknownSymbolError`, POST /ingest, /proposals/execute, in-app scheduler) rebuilds the portfolio from `list_positions()` only, sees held=0, re-proposes the same delta, mints a fresh `ord-{uuid4}` — so broker-side client_order_id idempotency can never fire — and submits again. Both fill: double exposure, doubling again per retry.
- Fix sketch: derive `client_order_id` deterministically (e.g. `ord-{sleeve}-{symbol}-{side}-{cycle-date}`) so the broker dedupe actually works across runs; and consult `broker.list_orders()` for open orders before sizing, counting pending quantity as held.

**F6. No serialization on the evaluate-to-place path: concurrent evaluations place duplicate real orders**
`application/evaluate_signals.py:88-101` (the code comment at :97-101 concedes the hole)
- Scenario: double-click on Execute proposals, or /proposals/execute overlapping the scheduler/POST /ingest/cron. Two `execute()` coroutines both snapshot account/positions before either places, compute the same delta, and submit with distinct uuid keys. The risk gate doesn't help — each run seeds its own `remaining_buying_power` from a pre-order snapshot.
- Fix sketch: per-sleeve `asyncio.Lock` around `execute()` for in-process overlap, plus a Postgres advisory lock for the cron-vs-web cross-process case. Pairs with the deterministic COID from F5.

**F7. SELL fill with no locally recorded BUY aborts the event append inside the transaction; newest-first order sync then wedges permanently**
`infrastructure/persistence/postgres_read_model.py:104`, `domain/positions.py:99-102`, `application/sync_orders.py:92`, `brokers/alpaca.py:118-125`
- Scenario: a buy+sell both happen while fill ingestion is off (the default). On catch-up, Alpaca returns orders newest-first (no `direction` override), so the SELL is processed first; the projection's long-only guard raises inside the append transaction, the event is never recorded, `SyncOrders.execute` raises with no per-order isolation, and every subsequent run repeats identically — fill ingestion for the sleeve is permanently dead, and the BUY behind it never syncs either. Paper is safe (insertion order), so this is live-only and untested.
- Fix sketch: sort orders by submitted_at ascending before applying; wrap each order in try/except so one bad order can't wedge the loop; and make the projection tolerant (record the fill, clamp/flag the position) instead of raising inside the append.

**F8. SyncOrders freezes after the first recorded fill: boolean per-order dedupe vs Alpaca's cumulative fill snapshot drops every later partial-fill increment**
`application/sync_orders.py:110` vs the correct model at `application/apply_trade_update.py:103-106` (merged: 4 findings)
- Scenario: 100-share order polled at 40 filled → records 40; order completes to 100 → every later poll skips it (`client_order_id in already_filled`), the remaining 60 shares are never recorded, `_sync_status` still flips it to FILLED. Positions/P&L permanently understate; reconcile reports unhealable drift forever; also poisons the poller as the stream's fallback (a stream-recorded partial blocks the poller from ever recording the remainder). Feeds a mis-sized full-position SELL later, which can trigger F7.
- Fix sketch: replace the boolean gate with the cumulative-increment logic ApplyTradeUpdate already has: record `broker_filled_qty - locally_recorded_qty` when positive. Add a partial-then-complete test.

**F9. Poller/stream check-then-act race double-records fills; the event store's IntegrityError retry converts the only concurrency signal into a success**
`application/apply_trade_update.py:80-107`, `application/sync_orders.py:80-96`, `infrastructure/persistence/postgres.py:35-67` (merged: 2 findings)
- Scenario: both paths are read-log-snapshot → await network → append, on the same event loop, with no lock. A fill arriving during the poller's `list_orders()` round trip gets appended by both; the `(stream_id, seq)` constraint is used only to allocate seqs (retry-with-fresh-seq), never as optimistic concurrency, so both writes commit. Position doubles in the projection, permanently (append-only log), with drift alarms forever.
- Fix sketch: single-writer rule (suppress poller fill-recording while the stream is connected) or per-order serialization; better, add expected-version CAS to `append()` (fail, don't retry, on seq conflict for these writers) and re-read on conflict.

**F10. MODE_DEFAULT=live boots every sleeve straight into live routing, bypassing the entire readiness gate with no audit event**
`config.py:36`, `main.py:294-306`, vs the only guarded entrance at `application/live_trading.py:203-212`
- Scenario: ALLOW_LIVE=true + live creds + MODE_DEFAULT=live (unvalidated env field) routes all orders to the live account from the first cycle: no caps-vs-live-ceilings check (MAX_TRADE_PCT_OF_SLEEVE=50 sails through where the API path refuses >5), no reconciliation check, no confirm, and no SLEEVE_MODE_CHANGED/USER_ACTION event — the system of record shows live trading with no record of entering live mode.
- Fix sketch: a config validator rejecting `mode_default=live` (boot always paper; live only via the gated API path). If you ever want boot-live, run AssessLiveReadiness at startup and append the audit events.

**F11. House PTR transaction side misclassified: first-standalone-P/S/E regex matches inside asset names ("S&P", "J.P.", single-letter tickers) — reproduced against the real parser**
`infrastructure/data_sources/house_disclosures.py:104` (`_TXN_TYPE_RE`), `:669-679`
- Scenario (reproduced): a PURCHASE of an "S&P …" fund parses as a SALE (the standalone S in "S&P" wins); a SALE of "J.P. Morgan…" parses as a PURCHASE; ticker "(S)" inverts; a standalone "E" silently drops the row as an exchange. Wrong-side signals flow into the live event log/rm_signals and into the BACKFILLED research corpus, poisoning the labels the algo is trained on — S&P-branded funds are among the most common PTR assets.
- Fix sketch: anchor the code search positionally — after the ticker parenthetical / immediately before the date column — instead of first-match-anywhere; add S&P / J.P. / single-letter-ticker fixtures. Consider a targeted relabel/backfill of affected rows afterwards.

**F12. Auth fails open by default: order-placing and risk-control endpoints are internet-exposed when API_KEY is unset**
`interface/auth.py:35,51-52`, `config.py:268`; contrast the refuse-to-start guard at `main.py:314-326` (merged: 3 findings)
- Scenario: Render URL is public; API_KEY unset (the default — DEPLOY.md never mentions it, and a dropped env var during a migration recreates it silently) exposes POST /proposals/execute, /kill-switch {engaged:false}, /cycle/mode {auto}, /sleeves/{id}/mode to anyone. Only signal: one startup log line. Live still needs ALLOW_LIVE + readiness, so blast radius today is the paper book plus the risk-control state that guards the eventual live path — becomes critical the moment ALLOW_LIVE is set.
- Fix sketch: refuse to start when a real Alpaca broker is wired and api_key is None (mirroring the market-data guard), or require an explicit ALLOW_UNAUTHENTICATED=true. Document API_KEY in DEPLOY.md.

**F13. Senate eFD stamps created_at with the TRANSACTION date, not the filing date: trades disclosed >21 days after the fact are silently and permanently dropped, the rest mis-aged**
`infrastructure/data_sources/senate_efd.py:199-201` (same defect in `congress_trades.py:63-65`, off by default)
- Scenario: STOCK Act allows 45-day filing lag; any transaction whose trade date is older than the 21-day cursor at disclosure time is dropped on every run forever, with no counter or log. Survivors decay from the trade date, so a trade disclosed on day 20 contributes almost nothing and ages out the next day. Directly contradicts the House adapter's PIT rule (created_at = FilingDate) despite the docstring claiming the same rules.
- Fix sketch: `created_at = filing.received` (disclosure time), keep the transaction date in the payload for decay/analysis decisions made explicitly. Add a dropped-row counter to ingest logging.

### MEDIUM

**F14. Async fill ingestion is disabled in every documented deployment; the system of record never records executions and drift is surfaced but never healed**
`config.py:257` (`order_sync_interval_seconds=0`), `config.py:284` (stream off), `jobs/cycle.py:59-79` (no sync step), `application/reconcile.py:82-93`
- The cron exits before orders fill; the poller and stream are both off by default and DEPLOY.md sets neither var. No fill of any cron-placed order is ever recorded; order statuses stay SUBMITTED; reconcile appends the same drift every run with no dedupe and no repair path. (Verification confirmed sizing reads the broker directly and snapshots are broker-sourced, so risk decisions and headline equity stay correct — this is projection/system-of-record integrity, hence medium.) Fix: run SyncOrders (+ a reconcile) at the end of the cron cycle and/or enable the poller in the deploy config; dedupe repeated identical drift.

**F15. Reconciliation (including the readiness reconciliation_clean check) is hard-pinned to the paper book — a live sleeve produces perpetual false drift and the live account is never reconciled**
`main.py:378-383`, `application/reconcile.py:59-65`, `application/live_trading.py:138-147` (merged: 3 findings)
- Once any sleeve goes LIVE, its fills enter the projection but reconcile diffs against the paper account: every live position = spurious drift forever, genuine live-account drift (manual trades, cancels, splits) never checked, and any later readiness re-assessment fails for the wrong reason. With ENABLE_ALPACA_PAPER=false + ALLOW_LIVE, "reconciliation" runs against the in-memory simulator. Fix: reconcile per venue — one reconciler per real account actually in use (paper book vs live book), splitting the local projection by sleeve mode; wire the live reconciler into readiness.

**F16. Runtime cycle-mode disarm is process-local and unpersisted: 'manual' in the UI does not stop the cron, and a restart silently re-arms auto**
`interface/app.py:480-486`, `config.py:78`, `jobs/cycle.py:56-58` (merged: 2 findings)
- POST /cycle/mode mutates only web-process memory (no event appended, unlike kill-switch); the cron reads CYCLE_TRADE_MODE from env fresh each run, and a web redeploy reverts to the env default. The code comment asserts the opposite guarantee. Fix: persist mode changes as an event (USER_ACTION + a mode-changed event) and have build_dependencies replay the latest; at minimum append the audit event and fix the comment.

**F17. Shared-pool buying-power guard disables itself when buying power is exhausted (0 doubles as the 'unknown' sentinel), and the resulting broker reject aborts the cycle mid-loop, skipping SELLs**
`application/risk.py:114-118` (sentinel documented at :50), `application/evaluate_signals.py:193` (no try/except)
- A fully-invested account (buying_power=0) bypasses the pool guard for every BUY; Alpaca's 403 then raises OrderSubmissionError, which aborts the remaining decisions including risk-reducing SELLs and the portfolio snapshot. Fix: use `None` for "unknown", treat 0 as a real exhausted reserve (floor buys to 0 → clean REJECT); wrap per-decision placement in try/except so one reject can't kill the loop. (The mid-cycle clamp scenario was refuted — see appendix.)

**F18. Alpaca list_orders silently truncates at the 500-order page: growing false 'missing' drift that permanently fails the readiness reconciliation check**
`infrastructure/brokers/alpaca.py:118-125`, `application/reconcile.py:74-80`
- Local order history grows forever; the broker fetch is one page of the newest 500. Past ~500 lifetime orders (months of daily trading), every older filled order reports as broker='missing' drift, drowning real drift and bricking `reconciliation_clean`. Fix: paginate with the `after` cursor, or bound the local comparison window to the broker's fetch window.

**F19. rm_positions projection is a read-modify-write across concurrent append transactions — lost updates under READ COMMITTED**
`infrastructure/persistence/postgres_read_model.py:88-125`
- Two fills for the same (sleeve, symbol) from different order streams (stream task + poller, or cron process) both SELECT the same base quantity and UPSERT stale absolute values; one increment silently vanishes and the error compounds until a manual rebuild. Proposals size deltas from this table. Fix: `SELECT ... FOR UPDATE` on the position row inside the append transaction, or write relative SQL (`quantity = rm_positions.quantity + :delta`).

**F20. Backfill marks its dedupe table only after ALL appends: a mid-run crash breaks the documented re-run idempotency and permanently duplicates the research corpus**
`application/backfill_signals.py:153-165` (merged: 3 findings)
- Thousands of per-signal append transactions, then one batch `seen.mark()`. Any crash/OOM/connection drop in between leaves appended-but-unmarked events; the documented recovery (re-run the window) re-appends all of them, permanently (append-only; purge only targets SYNTHETIC). Execution-barred, so research-only blast radius — but this corpus tunes the strategy. Fix: mark per signal immediately after its append (mark is already idempotent), or chunk append+mark in small batches.

**F21. purge_synthetic --confirm races the live service: events committed between the log snapshot and the rebuild's DELETE lose their read-model rows silently**
`jobs/purge_synthetic.py:139,169`, `infrastructure/persistence/postgres_read_model.py:164-176` (merged: 2 findings)
- The rebuild truncates all rm_* tables and replays a snapshot taken minutes earlier while the app keeps appending (each append commits its rm rows). Anything in the window vanishes from projections until a future full rebuild; the job prints a clean report and exits 0. Fix: take a Postgres advisory lock shared with the appender (or re-read the log inside the rebuild transaction / assert max(event id) unchanged and retry), and document "stop the service first" as a hard requirement.

**F22. Data-source API keys leak into Render logs: keys sent as URL query params appear verbatim in httpx exception messages logged by ingest**
`application/ingest_signals.py:57-62`; key-in-URL at `congress_bills.py:216-223`, `fda_approvals.py:140-141`, `federal_register.py:207-210`, `congress_trades.py:54`
- Any 429/5xx (routine on these APIs) raises HTTPStatusError embedding the full URL including the key; `logger.exception` persists it. Empirically confirmed with httpx 0.28.1. Alpaca and header-based adapters are safe. Fix: move keys to headers where supported; otherwise sanitize the exception/URL before logging. Rotate the FMP key if these logs have already seen errors.

**F23. Unauthenticated /ws/quotes clients can permanently kill the shared live quote stream (any upstream error frame is treated as fatal auth failure)**
`interface/app.py:557-587,613-619`, `infrastructure/market_data/alpaca_stream.py:100-108,125-127,154-159`
- Anonymous client subscribes hundreds of junk symbols → forwarded uncapped to the ONE Alpaca socket → IEX symbol-limit error frame → stream task treats it as bad credentials and exits, never retried; junk symbols persist and re-poison reconnects. Fix: cap and validate symbols (count, charset, known-directory), treat non-auth error frames as non-fatal (log and continue), and remove client-added symbols on disconnect.

**F24. Account financials and the full event log are readable with no authentication even when API_KEY is set**
`interface/app.py:242,356,372,541` ("GET reads stay open" by design, `auth.py:8`)
- /capital (broker cash/equity/buying power — paper today, live later), /events (every signal, order, fill, decision), /positions/live, and the /ws/events firehose are open to anyone with the URL. Fix: when api_key is configured, require it on sensitive reads (at least /capital, /events, /ws/events); the SPA already sends the key for writes.

**F25. Live signal-id schemes collide, silently dropping distinct same-day transactions from rm_signals**
`sec_form4.py:434` (no owner/accession/row-index: a 3-officer same-day cluster buy — the most informative Form 4 pattern — collapses to one row) and `senate_efd.py:213` (day-granular id without side: a same-day buy+sell keeps an arbitrary side, page order decides). The historical paths already carry the fix (accession:index source_uids). Fix: bring the live ids up to the historical scheme (include owner/accession/transaction index; include side+index for eFD).

**F26. House PTR amount bracket can be mis-attributed from a NEIGHBORING row (ascending-order search over a 4-line window) — reproduced**
`house_disclosures.py:632-634,701-705`
- With single-line rows two lines apart, a $250k-$500k trade inherits the neighbor's $1,001-$15,000 bracket (smaller brackets tried first, window spans transaction boundaries); not counted as a parse miss. Understates amount weighting and corrupts research payloads. Fix: constrain the bracket search to the current transaction's own block/line span, and prefer the bracket nearest the transaction line over the smallest that matches.

### LOW

**F27. CancelOrder's default-sleeve fallback imports foreign broker orders into sleeve-political's ledger**
`application/cancel_order.py:52,91`
- Cancelling an order the platform never placed (manual Alpaca-dashboard order, by COID) stamps it into sleeve-political's log; SyncOrders' "known" scoping then admits its fills, attributing a human trade to the algo, and a foreign partial SELL can trigger the F7 wedge. ## 3. What came back clean

- **Risk-gate topology**: every order provably passes `RiskGate.evaluate`; both auto-cycle and manual execute funnel through `EvaluateSignals`; no endpoint or job reaches `PlaceOrder` directly; no inverted conditions in the ALLOW_LIVE / readiness wiring.
- **Provenance wall**: `ensure_real_signals` abort + `tradeable_signals` filter are correctly ordered ahead of the strategy, and every deserialization path defaults unknown provenance to SYNTHETIC (fail-closed). BACKFILLED/SYNTHETIC signals cannot reach order intent.
- **Append-only enforcement**: migration 0001's DB triggers genuinely reject UPDATE/DELETE/TRUNCATE on events; no code path mutates the log; committing read-model rows inside the append transaction is a sound design (the defects above are in the layers on top, not the store's core invariant).
- **Money arithmetic**: consistently Decimal, floor rounding on share quantities, zero/negative-quantity rejection.
- **Credential separation**: no paper/live credential cross-fallback anywhere; Alpaca creds travel in headers; risk caps are required config with no defaults; settings are read at call time, not import time; DSN normalization is sound.
- **General security hygiene**: no pickle/eval/yaml.load; SQL is SQLAlchemy Core with bound parameters; API-key comparison is constant-time; all external data sources are off by default.
- **Async adapter hygiene**: WebSocket consumers are cancel-safe with capped backoff; every httpx client has a timeout; 429 retry honors Retry-After with a cap; retries are GET-only; background tasks are cancelled and gathered on shutdown.
- **Jobs/CLI discipline**: every job defaults to dry-run with no write reachable before --confirm; teardown always runs; the label store's replace_run is genuinely transactional (mid-write crash rolls back cleanly).
- **Historical/backfill adapter engineering**: source_uid dedupe via backfill_seen, PIT-correct acceptance timestamps, throttling, content-shape index parsing — the live paths should be brought up to this standard (F1, F13, F25), not the other way around.

## 4. Refuted / checked-and-cleared appendix

These claims were raised during review, adversarially checked, and cleared — no action needed:

- "Missing fill events cause unsafe over-trading" — refuted: risk sizing reads `broker.get_account()`/`list_positions()` directly, so the projection gaps in F8/F14 do not feed order sizing.
- "Equity/P&L headline goes stale without fill ingestion" — refuted: a broker-sourced PORTFOLIO_SNAPSHOT is written every cycle (`evaluate_signals.py:211-230`).
- "The buying-power guard re-disables itself mid-cycle via the clamp-to-zero feedback" — refuted: while active, the guard caps approved notional against the same price used for the subtraction, so the reserve never goes negative mid-cycle; only the start-of-cycle exhausted-zero case (F17) is real.
- "SyncOrders loses fills to the 500-order page truncation" — effectively unreachable (would require 500+ orders between consecutive syncs); only the Reconcile false-drift path (F18) is real.

## 5. Suggested fix order (for task specs)

1. F1 (replay dedupe + persisted cursors) — blocks auto mode; stops ongoing log corruption today.
2. F2 + F3 (persist/rehydrate kill switch and peak equity from the event log) — one task, same mechanism.
3. F5 + F6 (deterministic client_order_id + open-order awareness + per-sleeve lock/advisory lock).
4. F4 (kill the synthetic price fallback under require_real_data).
5. F8 + F9 + F7 + F14 (fill-ingestion overhaul: cumulative-increment model, single-writer or CAS append, oldest-first + per-order isolation + tolerant projection, enable sync in the cron).
6. F11 + F13 (parser side/timestamp fixes + targeted relabel) — protects the research program feeding the gate decision.
7. F12 + F10 (fail-closed auth, reject MODE_DEFAULT=live) — cheap, do before any live milestone.
8. Remaining mediums (F15-F26) as a pre-live hardening batch; F27 anytime.
